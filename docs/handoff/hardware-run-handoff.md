## Tool facts the script assumes

- Every audio result carries `probable: true`; say so when you report BPM,
  key, downbeat, classes and notes. `analyze_reference` reports which
  separator and beat tracker actually ran (`separation.method`,
  `beat_tracker.method`); with `auto` expect `demucs` and `beat_this`, both
  cached on this machine.
- `extract_kit` returns `install_mapping` in exactly the shape `install_kit`
  takes and `required_pcm_bytes` equal to what its preflight will count.
  `unfilled` pads are listed with a reason; that is normal, not an error.
- `transcribe_groove` transcribes only kick/snare/hat pads. If the groove
  comes out rotated by a beat, pass `downbeat_s` — do not edit strings by
  hand. Its `pattern` is passed to `generate_ppak` verbatim.
- `generate_ppak` never overwrites `out`, refuses a template that is not in
  the device's own TAR flavour, and lists every changed byte range in
  `manifest`. Compare the manifest with the expected diff in the script
  *before* the owner imports. `include_sounds=true` with a `.pak` template
  copies the sounds the project's pad records reference — the same shape as
  a Sample Tool export. Rung 3 uses the `add` form (append events, keep every
  existing byte); rungs 4 and step 4 use the `steps` form.
- `install_kit` returns `needs_confirmation` with the full impact first. Show
  it to the owner verbatim, wait for an explicit yes, then repeat the call
  with `confirm`. It is not a transaction; read every entry's status.

## Rules that do not relax

- One MIDI owner: no `tools/*.py` while the server is up; Sample Tool closed
  whenever the server runs. The script marks which is which.
- Fresh backup before each rung; every import into the non-active project.
- Stop at the first failure. Write it up in
  `docs/research/reference-to-song-run.md` before the next device-touching
  step; then continue with the parts that do not depend on it (step 2 never
  depends on the ladder; step 4 does).
- Never print the serial (`device_info` omits it by default). Never commit
  `*.pak`, `*.ppak`, clips, stems or slices.
- No `git` history rewriting; Conventional Commits; one commit per step of
  write-up if you commit during the session.

## Known gaps to keep in mind

- ZIP container parity with Sample Tool's own writer (flag bits, extra
  fields) was not attempted; rung 2 is the test. If rung 2 fails and rung 1
  passed, compare `unzip -v` of both `.ppak`s and record the difference.
- Pad records are 26 or 27 bytes; the generator patches only slot and length
  and keeps the rest. Sample Tool's import tolerance for either size is
  unknown.
- Velocity is unproven (`o` == `x`), event byte 7 is written as 0 (a
  device-produced value), bass and melodic pads get no pattern yet.
- The librosa fallback guesses the downbeat from kick energy; on real
  material with Beat This! this should not come up.
